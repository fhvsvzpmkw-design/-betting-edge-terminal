# Public Ledger Operations

## Purpose

The public ledger is the single customer-facing betting-history contract for VigWire Labs. It exists so public modules can read sanitized betting history without ever requiring access to the private master ledger.

## Canonical paths

- **Canonical public ledger:** `data/ledger/public-ledger.json`
- **Legacy compatibility copy:** `data/bet-history-public.json`
- **GitHub Pages API compatibility copy:** `api/bet-history`
- **Live canonical API:** `/api/bet-history`

Only `data/ledger/public-ledger.json` is intended to be manually replaced or supplied by a future customer upload flow. The two compatibility copies are generated by automation and must not be treated as independent sources of truth.

## Privacy boundary

The private master ledger is background-only and must never be published into the public repository or exposed directly to F3 Bet History, Eddie Numbers / Muddy Numbers, hotline pages, or other customer-facing modules.

Current production can derive a sanitized `/api/bet-history` response from the private master ledger in the Cloudflare Worker. The stable public-ledger file provides the parallel upload/static contract. Both must satisfy the same public schema and privacy rules.

Public rows must not expose the private sportsbook/account reference in row index `2`; that position must remain `null` in the public projection.

## Customer/public ledger update procedure

For a manual update today, or a future customer upload workflow:

1. Produce a sanitized schema-2 public ledger JSON file.
2. Keep `publicProjection: true`.
3. Verify `wagers` is an array and `validation.uniqueWagers` equals the wager count.
4. Verify every wager has `null` at row index `2`.
5. Replace **only** `data/ledger/public-ledger.json` while keeping the filename and path unchanged.
6. Allow `Public Ledger Sync` to validate the canonical file.
7. The workflow copies the exact canonical bytes to `data/bet-history-public.json` and `api/bet-history`.
8. Muddy Numbers ledger tests verify the canonical ledger, compatibility copies, public-only authority, and no private-ledger leakage.
9. Confirm F3 Bet History and Muddy Numbers load successfully after deployment.

If validation fails, the compatibility copies must not be updated. Fix the uploaded canonical public ledger rather than patching downstream consumers.

## Consumer rule

Public-facing modules consume the public ledger contract. They do not choose between private and public data and do not know private ledger locations or credentials.

- F3 Bet History: public ledger projection only.
- Eddie Numbers / Muddy Numbers: public ledger projection only.
- Public performance/history modules: public ledger projection only.
- Private accounting/bankroll processing: may use the private master ledger behind the server boundary, then sanitize before exposure.

## Compatibility rule

`data/bet-history-public.json` and `api/bet-history` exist to support current readers while the canonical storage path is standardized. They are generated compatibility surfaces, not editable ledgers.

A direct edit to either compatibility file is considered drift and should fail ledger validation because both copies must be byte-identical to `data/ledger/public-ledger.json`.

## Future customer upload model

The intended customer model is:

**customer/private accounting source → sanitization boundary → canonical public ledger → validated public consumers**

A customer may eventually upload an already-sanitized public ledger directly. That does not require changing F3, Muddy Numbers, or other public consumers as long as the canonical public-ledger contract remains stable.

The private ledger can continue to exist separately for richer accounting, bankroll, and internal processing. The public repository and public pages never require that private file.

## Recovery

If a public-ledger update causes a failure:

1. do not modify the private master ledger as a display repair;
2. inspect `data/ledger/public-ledger.json` first;
3. restore the last known-good canonical public ledger from Git history if necessary;
4. rerun `Public Ledger Sync`;
5. verify the compatibility copies and Muddy Numbers validation;
6. verify the live public pages.

This keeps ledger recovery isolated from Betting Edge Core, report history, and betting-analysis logic.
